## Context

Persistent game state outlives scene instances, but a single large manager is difficult to maintain as party, progress, player state, statistics, quests, and save data grow.

## Decision

Keep `GameManager` as the compatibility facade and singleton access point, while durable state lives in focused managers such as `PartyManager`, `ProgressManager`, `PlayerStateManager`, and `StatsManager`.

## Rationale

`GameManager` constructs focused sub-managers, exposes direct getters, and preserves existing public methods as delegation calls. `SaveManager` serializes/deserializes through the facade so callers do not need to know every focused store.

## Consequences

Existing consumers can continue using `GameManager`, but new focused state APIs should live in the sub-manager that owns the data. Tests still need singleton reset discipline because the facade and some sub-managers remain process-level singletons.

## Unknowns

The split is partial. Many callers still import `GameManager` directly, and concurrent manager/system work may change which focused store owns individual fields.
