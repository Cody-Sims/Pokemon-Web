## Context

The data layer carries many string and numeric references among Pokémon, moves, items, trainers, shops, encounters, maps, quests, cutscenes, and achievements. Broken references and executable data helpers previously made those contracts fragile.

## Decision

Keep registry data declarative and side-effect free, derive typed IDs from registries where practical (`MoveId`, `MapKey`), put lookup logic in selectors instead of data records, and enforce cross-registry references with integrity tests.

## Rationale

Move and map registries derive ID unions from `as const` registry objects. `selectors.ts` centralizes lookup behavior and throws `MissingDataError` at the boundary. `data-integrity.test.ts` validates dangling references across the major registries, including shop inventories keyed to shop-host maps.

## Consequences

Data additions must update the appropriate registry/barrel and satisfy integrity tests. Runtime code should prefer selectors for lookups that need explicit failure instead of fallback labels.

## Unknowns

The data layer still contains parser and selector helper functions under `frontend/src/data/`, so the purity rule applies to declarative content records rather than every TypeScript file in the directory.
